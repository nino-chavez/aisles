# Decision Record: The Vocabulary Constraint Invariant

**Date:** 2026-04-10
**Status:** Accepted — enforced in code, now documented as first-class principle
**Context:** The foundational architectural principle that makes AI-generated layouts reliable in production

## Summary

Aisles enforces a formal correctness invariant on every AI-generated layout:

> **For all possible user inputs I and all possible personalization vectors P, the layout generation function f must produce an interface state S that is an element of the set V of valid configurations.**
>
> **∀I, ∀P, f(I, P) → S ∈ V**

This is the invariant that separates a working AI commerce system from a demo that breaks in production. It is enforced through a three-layer defense: a Zod schema that defines V explicitly, structured LLM output that constrains generation to V-compliant tokens, and a fallback cascade that guarantees a valid S always exists.

The invariant was implicit in the codebase since the first layout generation commit. This ADR promotes it to a first-class architectural principle with explicit documentation, measurement, and evolution governance.

---

## The Problem

### Traditional Software Testing Assumes Determinism

In a deterministic system, QA works by enumerating inputs and verifying outputs. Input `{persona: 'hunter', category: 'furniture'}` always produces the same layout. You write a test case, you verify it, you move on. Coverage is the question — how many inputs have you tested?

This breaks when the output is generated by a non-deterministic LLM. The same input can produce different outputs on different calls. The output space is effectively infinite. You cannot enumerate test cases because there are no stable cases to enumerate.

### Two Failure Modes Without Constraint

AI-generated UI systems typically fail in one of two ways:

**Mode 1: Free-form generation.** "Let the AI write HTML" or "Let the AI generate React components." The output is wildly inconsistent — sometimes brilliant, sometimes broken, sometimes subtly wrong in ways that only manifest for specific shopper combinations. These systems work in controlled demos but fail in production because the failure rate is low enough to miss in QA and high enough to destroy merchant trust at scale.

**Mode 2: Oversized vocabulary.** "The AI can choose from 200 components with flexible props." The output is technically valid but unpredictable. The AI makes strange composition choices. Merchandisers cannot reason about what the layout will look like for any given input. Visual regression becomes impossible because the possibility space is too large to sample meaningfully.

The root cause in both modes is the absence of an enforceable constraint on the set V. Without a finite, typed, validated definition of "valid output," you cannot guarantee the invariant holds, and you cannot test that it does.

### Why This Matters More Than It Looks

The invariant is the boundary between a demo and a product. A demo works because you hand-pick the inputs that produce good outputs. A product works because it handles every input. Every AI UI system that has ever shipped has faced this boundary. The systems that shipped successfully solved it with an explicit constraint on V. The systems that failed either did not recognize the constraint was necessary or could not define V tightly enough to enforce it.

This is the single most important technical decision in Aisles. The inference engine, the signal pipeline, the layout cache, and the Observe dashboard all depend on this invariant holding. If V is ill-defined, the entire system becomes unreliable. If V is well-defined and enforced, the system becomes reliable enough to ship to merchants who have no patience for AI flakiness.

## The Decision

Aisles enforces the invariant through a three-layer defense.

### Layer 1: The Zod Schema Is the Definition of V

The set V is not implicit or described in prose — it is literally the Zod schema in `src/lib/schema/layout.ts`. Every valid layout is an object that passes Zod validation against this schema. Every invalid layout fails validation and is rejected.

The schema defines:

- **Persona**: must be one of `'gatherer' | 'hunter' | 'researcher' | 'gifter'` — four values, nothing else
- **Reasoning**: a string describing the AI's rationale (used by the Observe dashboard)
- **Sections**: an ordered array of section objects drawn from a typed union
- **Current component types**: `editorial-header`, `hero-product`, `product-grid`, `category-header`, `editorial-hero`, `lifestyle-price-hero`, `image-gallery`, `product-carousel`, `category-tile-grid`, `service-callouts-grid`, and `cluster-chip-row`; generation receives a narrower subset for each persona
- **Component props**: typed per component (e.g., `product-grid.columns` must be `2 | 3 | 4`, `imageRatio` must be specific enum values)
- **Product references**: the `productOrder` field contains product IDs that must exist in the catalog passed to the prompt

**Decision baseline:** when this ADR was accepted on 2026-04-10, the vocabulary
contained four component types: `editorial-header`, `hero-product`,
`product-grid`, and `category-header`. The current eleven-member union is an
implementation expansion after that decision. The original four-component
baseline explains this ADR's trade-off discussion; it is not the current-state
inventory.

The schema is enforceable: `LayoutSchema.safeParse(output)` returns either `{success: true, data}` or `{success: false, error}`. There is no ambiguity. An output is either in V or it is not.

### Layer 2: Structured LLM Output Constrains Generation

The current Vercel AI SDK v6 path passes the Zod schema through `Output.object` on `generateText` and `streamText`. The provider produces a structured result, and Aisles validates that result against the same schema before publication.

This dramatically raises the probability that the LLM's output is V-compliant. Claude Haiku 4.5 with a well-formed schema produces valid outputs at a high rate (currently not measured; see "Operational Consequences" below). Claude Sonnet 4.6 is more capable and produces valid outputs at a higher rate.

Structured output does not eliminate invalid outputs entirely. The schema constrains the *structure* but not the *semantic correctness*. A layout can be schema-valid but reference a product ID that doesn't exist, have an inconsistent reasoning string, or select components that don't make sense for the persona. It can also be structurally valid in Aisles's shared vocabulary while failing to preserve a merchant's visual or interaction system. Layer 2 handles structural validity; Layer 3 handles the current runtime failure modes. Reference preservation requires the planned versioned design contract and parity gates described in the [organization, brand, and composition autonomy plan](../organization-brand-autonomy-plan.md) and [Kibble boundary retrospective](../retrospective-kibble-reference-boundary.md).

### Layer 3: Fallback Cascade Guarantees S ∈ V

The `∀I, ∀P` guarantee is only meaningful if the system *always* produces a valid S. This requires a fallback cascade for when the primary path fails.

Current implementation:

1. **Primary**: Claude Haiku 4.5 with structured output. If the output passes schema validation, use it.
2. **Fallback 1**: Claude Sonnet 4.6 with the same structured output call. Used when Haiku produces a schema-invalid output or when Haiku fails entirely (timeout, rate limit, API error).
3. **Fallback 2**: Static Svelte fallback layouts per persona. Used when both Haiku and Sonnet fail. These layouts are not AI-generated — they are hand-written SvelteKit components that render directly without needing a schema-valid AI output.

The cascade means there is always a valid S. The worst case is a static fallback, which is less personalized but still functional. The invariant holds under all failure modes.

## Operational Consequences

Enforcing the invariant in code is necessary but not sufficient. The invariant must also be measured, governed, and protected as the system evolves.

### Measurement: Schema Validation Success Rate

There must be a health metric: **the percentage of LLM calls that produce schema-valid outputs on the first try**. This is the single most important operational metric for the AI layer of Aisles.

- **Above 95%**: healthy. The prompt is working, the schema is tight, the model is behaving.
- **90-95%**: warning. Investigate the failing cases. Is there a prompt regression? A schema change that confused the model? A product catalog with unusual properties?
- **Below 90%**: critical. The system is falling back to Sonnet frequently, which is slower and more expensive. Something is wrong.

This metric should be surfaced in the Observe dashboard as a top-level health indicator. It should be logged to the `generation_logs` table in Supabase Postgres alongside model, tokens, and cost. It should be monitored with alerting when it drops below threshold.

**Current state**: not measured. The logging infrastructure exists but does not separately track first-try validation success versus fallback usage. This is the first gap the ADR calls out for closure.

### Governance: The Vocabulary Evolution Process

Every addition to V (new component, new prop, new enum value) is a risk. The LLM now has more choices, which means more ways to produce an invalid output. The first-try validation rate may drop after a schema expansion.

The vocabulary evolution process:

1. **Design the new component.** What does it do? What are its props? What constraints apply?
2. **Add it to the schema** (`src/lib/schema/layout.ts`). Define the props as typed Zod fields. Add it to the discriminated union of section types.
3. **Add it to the prompt guide** (`src/lib/server/layout-prompt.ts`). The AI needs to know when to use the new component and how it differs from existing ones.
4. **Write a visual regression snapshot.** Render the new component with representative props and capture a baseline image.
5. **Run a staging validation sweep.** Generate layouts for a representative set of `(persona, category, product)` combinations and measure the first-try validation rate against the new schema. If the rate drops more than 2 percentage points, revise the prompt or narrow the component's prop space.
6. **Deploy.** Monitor the validation rate in production for 48 hours before considering the change stable.
7. **Invalidate the layout cache.** Cached layouts from the old schema may not be valid against the new schema. Flush the cache on deployment of any V change.

This process is mandatory for every V change. Skipping any step risks a production regression.

**Current state**: no documented process. Schema changes are made ad-hoc. The intent-driven commerce spec (`docs/specs/intent-driven-commerce.md`) proposes ten new component types, every one of which would be a V expansion that needs to go through this process. Without a documented process, adding these components will silently degrade system reliability.

### Cache Invalidation on Schema Change

The Redis layout cache stores layouts keyed by `persona + categorySlug`. These cached layouts are snapshots of V at the time they were generated. If V changes — a component is added, a prop type narrows, an enum value is removed — cached layouts may no longer be valid against the new V.

This must be handled explicitly. When the schema version changes, the cache must be invalidated. Options:

- **Schema versioning**: include a schema version hash in the cache key. A new schema version produces new cache keys, leaving old entries to expire naturally.
- **Explicit invalidation**: on deployment of a schema change, run a cache flush script as part of the deploy pipeline.

**Current state**: not handled explicitly. Schema changes rely on the 1-hour cache TTL to eventually flush stale entries. This is acceptable for minor changes but risks serving stale-and-invalid layouts for up to an hour after a schema change.

### Trade-Off: Vocabulary Size vs. Invariant Strength

There is an inverse relationship between the size of V and the tightness of the invariant:

- **Decision baseline (2026-04-10: 4 components)**: A small vocabulary gave the original system strong structural bounds and low layout variation.
- **Current V (11 components)**: The current union remains finite and generation narrows it per persona. Its first-try validation rate is not measured, so the current reliability trade-off is not quantified.
- **Large V (hypothetical: 20+ components)**: Weaker guarantees. Lower validation success rate. High layout variation. The AI has more creative freedom but produces more schema-invalid outputs.

The correct size of V is an engineering decision that depends on the reliability target and the variation budget. The current eleven-member vocabulary is still bounded, but its reliability trade-off needs measurement rather than an inherited four-component claim. Future expansions should proceed carefully.

Every expansion should be justified by a specific merchant or shopper need, not by a general desire for more flexibility.

### Visual Regression Across V × Persona

Schema validity is necessary but not sufficient. A component can be schema-valid but visually broken — a CSS regression, a prop interaction bug, a responsive breakpoint failure — or valid yet wrong for an external merchant's reference storefront. The invariant covers structural validity; visual regression covers rendering validity. Reference-specific desktop and mobile parity gates are planned, not present.

The visual regression suite should render:

- Every component in V
- Every combination of prop values that the AI can produce
- Across the four personas
- At mobile, tablet, and desktop viewports

This is a finite set because V is finite. It is tractable to test exhaustively, unlike a free-form AI system. When implemented, the suite should run on every deployment and block merges that introduce visual regressions.

**Current state**: no visual regression suite exists. This is a gap to close before expanding V.

## What This Changes

### For the Architecture Documentation

The architecture overview should open with the invariant as the core architectural principle. Currently the architecture doc starts with the tech stack and jumps into the signal pipeline. The invariant should be the first concept introduced because everything else depends on it.

### For the Product Vision

The product vision's "invisible to shopper, transparent to operator" principle depends on the invariant. The Observe dashboard can only be transparent if the AI's output is constrained to a known vocabulary. The invariant is the *reason* transparency is possible.

### For the Competitive Moat Analysis

The moat document lists the vocabulary constraint as one of four hard-to-replicate capabilities. It should be promoted to the primary technical moat. Every other technical capability (the inference loop, the enrichment pipeline, the Observe dashboard) depends on the invariant holding. If a competitor does not recognize this, they will build a system that works in demos and fails in production.

### For the Intent-Driven Commerce Spec

The spec proposes ten new component types. Each one is a V expansion that must go through the vocabulary evolution process defined in this ADR. The spec should reference this ADR as a prerequisite for any component additions.

### For the Observe Dashboard

The dashboard should surface the schema validation success rate as a top-level health metric. Currently the dashboard shows signal activity, persona inference, and layout generation outputs, but does not show the rate at which those outputs are first-try valid versus fallback-derived.

## Alternatives Considered

### Alternative 1: Free-Form AI Generation

Let the LLM generate free-form HTML, JSX, or Svelte markup. The pipeline parses whatever the AI produces and renders it.

**Rejected because**: This is Mode 1 of the failure modes described above. It has never worked reliably in production for any known AI UI system. The failure rate is too high to ship to merchants.

### Alternative 2: Fine-Tuned Model on Custom Layout DSL

Fine-tune a smaller model on a custom domain-specific language for layouts. The model learns the DSL and produces valid outputs by training rather than by schema constraint.

**Rejected because**: Fine-tuning is expensive, slow to iterate, and locks the system into a specific model. The structured output approach with Claude Haiku achieves similar reliability at a fraction of the cost and iteration speed. Fine-tuning may become relevant if Claude's structured output capability regresses or if cost pressures demand a smaller model.

### Alternative 3: Rule-Based Layout Assembly

Skip the AI entirely. Define layout rules ("if persona is hunter, show category-header + 4-column grid") and deterministically assemble layouts from the rules.

**Rejected because**: Rules cannot produce the editorial copy, the reasoning, or the nuanced product ordering that the AI provides. Rule-based systems are more reliable but less personalized. The constrained AI approach gets the reliability of rules with the personalization of AI.

### Alternative 4: Large Vocabulary with Soft Constraints

Define a large V (20+ components) but use "soft" validation — accept any output that is *mostly* valid and patch the invalid parts.

**Rejected because**: Soft validation is how AI UI systems fail slowly. Each patched output is a small compromise. Over time, the compromises accumulate and the system becomes unreliable. Hard validation with a small V is more honest about the trade-off and more defensible in production.
